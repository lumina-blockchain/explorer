P2P Gossipsub & Mesh Routing

Mekanisme Penghematan Bandwidth & Proteksi Banjir Data Broadcast pada Blockchain Lumina

Dalam topologi jaringan Blockchain peer-to-peer (P2P), setiap node staker terhubung ke banyak node tetangga demi menjaga ketersediaan jalur komunikasi. Namun, hal ini memicu bahaya laten: jika setiap node menyebarkan (broadcast) transaksi atau blok baru ke semua peer yang terhubung secara membabi buta (disebut Naive Flooding), jaringan akan mengalami kemacetan lalu lintas data (congestion) akibat transmisi duplikat yang mubazir.

Untuk menjamin efisiensi bandwidth yang luar biasa dengan latensi mikrodetik, Lumina mengadopsi protokol libp2p Gossipsub (Gossip + Subscription) terintegrasi dengan Kademlia DHT Self-Healing Peer Discovery.

Filosofi Efisiensi: Amankan redundansi koneksi fisik untuk ketahanan jaringan, namun minimalkan transmisi data logis untuk efisiensi bandwidth!

1. Anatomi Gossipsub: Mesh vs Gossip

Gossipsub membagi koneksi fisik aktif di dalam jaringan menjadi dua lapisan logis untuk menyeimbangkan keandalan dan efisiensi:

Mesh Peers (Aktif & Cepat)

Node secara dinamis memilih sebagian kecil dari peer terhubungnya (biasanya 4 hingga 8 peer) sebagai "Mesh". Begitu ada blok atau transaksi baru, data payload utuh langsung dipush secara instan ke node-node Mesh ini untuk transmisi super cepat.

Gossip Peers (Hemat Bandwidth)

Untuk semua peer di luar lingkaran Mesh, node kita tidak akan mengirimkan payload utuh. Kita hanya menyiarkan bisikan metadata berupa pesan IHAVE yang super ringan berisi daftar hash pesan. Node lain hanya akan meminta data penuh via IWANT jika ia belum memilikinya.

2. Seen Message Cache (Proteksi Duplikasi)

Bagaimana jika dua peer mengirimkan transaksi yang sama pada detik yang sama? Di sinilah peran Seen Message Cache (in-memory) di dalam runtime rust-libp2p:

Setiap pesan P2P yang melintasi node Lumina memiliki pengidentifikasi unik (Message ID / Hash). Node menyimpan catatan hash pesan yang baru saja diterima di dalam cache berkecepatan tinggi. Jika ada peer lain yang mencoba membroadcast pesan dengan hash yang sama, sistem akan langsung membuangnya di gerbang masuk tanpa membuang-buang resource CPU untuk parsing atau validasi ulang!

3. Auto-Mesh DHT & Self-Healing (Kademlia + Identify)

Pada internet publik (VPS / Cloud Server), protokol broadcast lokal seperti mDNS diblokir oleh router dan ISP. Jaringan Lumina mengatasi hal ini dengan mengombinasikan Identify Protocol dan Kademlia DHT Bootstrap secara otomatis.

Di dalam main loop main.rs, Lumina mendengarkan informasi multiaddress eksternal yang dipertukarkan selama jabat tangan (handshake) awal:

// 1. Tangkap alamat eksternal via Identify Protocol libp2p::swarm::SwarmEvent::Behaviour(lumina_network::behavior::LuminaEvent::Identify( libp2p::identify::Event::Received { peer_id, info, .. } )) => { for addr in info.listen_addrs { // Masukin ke Kademlia DHT & Gossipsub network.swarm.behaviour_mut().kademlia.add_address(&peer_id, addr.clone()); network.swarm.behaviour_mut().gossipsub.add_explicit_peer(&peer_id); } }

Sesaat setelah koneksi stabil terbentuk, node baru akan langsung memicu query bootstrap Kademlia DHT:

// 2. Lakukan Kademlia Bootstrap untuk auto-discovery libp2p::swarm::SwarmEvent::ConnectionEstablished { peer_id, .. } => { rpc_context.scoring.write().unwrap().set_connected(peer_id, true); // Picu bootstrap agar menanyakan peers lain ke bootnode if let Err(e) = network.swarm.behaviour_mut().kademlia.bootstrap() { tracing::warn!("⚠️ Failed to trigger Kademlia bootstrap: {:?}", e); } }

Ketahanan Jaringan 100% (Zero-Downtime)

Berkat kombinasi ini, begitu satu node (seperti Bootnode utama) mengalami offline/mati, node-node lainnya yang telah saling mengenal (VPS 2, VPS 3, VPS 4) akan **tetap mempertahankan komunikasi mesh langsung** di antara mereka. Konsensus tidak akan pernah berhenti dan node tidak akan terisolasi sendirian!
