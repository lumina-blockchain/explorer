2. Anatomi Bug: Byzantine Race Condition

Penyelidikan mendalam terhadap mesin konsensus HotStuff BFT Lumina L1 menyingkap sebuah **Race Condition** yang terjadi ketika node sedang sibuk memproses catch-up sync.

Secara default, ada dua jalur terpisah di mana node validator aktif dapat memberikan suara (*Vote*):

Jalur 1: Proposal Blok Mandiri

  • Terjadi di dalam generator interval block_timer.
  • Jika node ditunjuk sebagai round leader atau mendeteksi timeout leader sebelumnya, ia merakit dan mengusulkan blok baru miliknya sendiri.
  • Node kemudian secara otomatis menandatangani blok proposalnya sendiri (Self-Vote) untuk disebarkan.

Jalur 2: Penerimaan Blok Jaringan

  • Terjadi ketika pesan Gossip berisi blok baru berukuran valid diterima dari jaringan P2P.
  • Node memverifikasi QC blok tersebut, mengeksekusi state lokal, dan mengirimkan suara persetujuan (Vote) kepada leader putaran.

Ketika Node-2 sedang mengejar ketertinggalan blok #233, ia menerima blok #233 sah dari jaringan Gossip dan memberikan suara setuju untuk Hash 0x927ca5.... Namun, pada detak milidetik yang sama, scheduler internal memicu event block_timer. Karena node belum menyelesaikan transisi database, ia merasa terpilih menjadi leader untuk tinggi #233 yang kosong, merakit blok usulannya sendiri dengan Hash 0x5e3568..., menerapkan blok tersebut ke database lokalnya, dan memberikan suara setuju untuk proposalnya sendiri.

Akibat ketiadaan **memori penanda** mengenai ketinggian yang sudah pernah dipilih dalam eksekusi lokal, Node-2 menandatangani kedua suara tersebut. Hal ini melanggar kaidah keselamatan quorum (*quorum safety*), karena validator BFT tidak boleh memberikan suara untuk dua blok berbeda pada tinggi yang sama!

4. Solusi: Implementasi Perisai Idempotensi BFT

Untuk mengatasi celah Byzantine ini secara permanen tanpa menambah overhead disk I/O yang berat, kita mengimplementasikan sistem pelacakan state **last_voted** lokal secara *thread-safe* di dalam event loop utama mesin konsensus.

Kita mendefinisikan penanda lokal in-memory sebelum event loop dijalankan:

let mut last_voted: Option<(u64, Hash)> = None;

Sebelum tanda tangan BLS dibuat baik di Jalur 1 (Leader Self-Proposal) maupun Jalur 2 (Gossip Block Auto-Vote), kita menyuntikkan fungsi evaluasi keamanan berikut:

let block_hash = block.hash(); let target_height = block.header.number; let can_vote = match last_voted { Some((voted_h, voted_hash)) => { target_height > voted_h || (target_height == voted_h && block_hash == voted_hash) } None => true, };

Kaidah Keamanan Perisai:

1. **Ketinggian Lebih Baru (target_height > voted_h)**: Validator diizinkan memberikan suara karena konsensus telah maju ke babak baru.
2. **Keandalan & Idempotensi (target_height == voted_h && block_hash == voted_hash)**: Jika validator diminta mengirim ulang suaranya untuk blok yang sama (misalnya karena kehilangan paket P2P), ia diizinkan untuk mengirim ulang demi kelangsungan jaringan (*liveness*).
3. **Blok Berbeda (Kondisi Gagal)**: Jika target_height == voted_h tetapi block_hash != voted_hash, ia terdeteksi sebagai upaya Double-Voting. Sistem akan membatalkan pemrosesan vote dan memancarkan log penolakan otonom.

6. Kesimpulan

Kejadian post-mortem ini menegaskan kembali pentingnya pertahanan berlapis di tingkat mesin konsensus dan agen jaringan. Integrasi perisai idempotensi in-memory terbukti tangguh dalam menahan kondisi balapan tanpa mengurangi liveness validator, sekaligus Sentinel Agent tetap bersiaga memotong validator yang terbukti sengaja berbuat Byzantine jahat. Lumina L1 kini jauh lebih kokoh di bawah tekanan skenario sabotase paling ekstrem sekalipun!
