BFT Slashing, Sybil Key Protection & Governance Appeal

Bagaimana Lumina L1 menjaga keamanan konsensus dari kecurangan fatal validator nakal, penyerangan identitas ganda (Sybil), serta memfasilitasi pemulihan desentralisasi berbasis voting suara aktif 75%.

Dalam sebuah jaringan blockchain Proof of Stake (PoS) publik terdesentralisasi, jaminan keamanan ekonomi adalah prioritas nomor satu. Tanpa adanya hukuman finansial yang tegas untuk pelanggaran konsensus, validator nakal dapat mencoba melakukan serangan pemalsuan sejarah transaksi atau manipulasi quorum tanpa resiko apa pun.

Lumina L1 memperkenalkan framework pertahanan keamanan terintegrasi tingkat lanjut: **BFT Slashing Engine**, **Sybil Key Protection**, dan **Decentralized Governance Appeal System** dengan ambang batas pemulihan **75%** kekuatan suara aktif.

🚨 Aturan Protokol: Validator yang terbukti melakukan pelanggaran fatal (seperti double-voting) akan langsung dijatuhkan hukuman pembekuan stake 98% selamanya dan 2% dibagikan sebagai hadiah Bounty kepada penemu bukti (Reporter)!

1. Severe Slashing (Pemberantasan Double-Voting)

Pelanggaran BFT paling fatal dalam sistem konsensus adalah **Double-Voting** (validator memberikan suara persetujuan untuk dua hash blok berbeda pada tinggi blok yang sama di putaran konsensus yang sama). Hal ini dapat memicu percabangan (fork) ilegal pada rantai.

Deteksi Real-Time oleh Sentinel Agent

Setiap node Lumina dilengkapi dengan **Sentinel Agent** yang berjalan di background dan memantau topik gossip suara (lumina-votes). Jika Sentinel mendeteksi dua vote sah yang bertentangan dengan tanda tangan BLS yang sama:

// Deteksi real-time Sentinel Agent di node/src/main.rs if let Some(prev_vote) = vote_collector.insert(vote.validator.clone(), vote.clone()) { if prev_vote.block_hash != vote.block_hash { tracing::warn!("🛡️ [Sentinel Agent] DETECTED DOUBLE-VOTING by {}!", vote.validator); let proof = SlashProof { vote_a: prev_vote, vote_b: vote.clone() }; // Susun transaksi SLASH dan siarkan ke mempool ... } }

Eksekusi Hukuman & Pembagian Bounty 2%

Ketika transaksi SLASH: diproses oleh Execution Engine di crates/state/src/lib.rs:

  1. Tanda tangan BLS pelaku diverifikasi secara matematis terhadap kedua pesan yang bertentangan.
  2. Status validator pelaku langsung diubah menjadi Jailed Severe.
  3. Status pencairan dana staker allow_unstake diset ke 0 (False) secara permanen.
  4. Sebanyak 2% dari total dana staker pelaku langsung diberikan sebagai Bounty ke reporter/penemu bukti.
  5. Sisa 98% dana staker pelaku dibekukan selamanya di dalam kas sistem.

2. Proteksi Sybil Key (Duplicate BLS Registry Prevention)

Serangan Sybil terjadi ketika satu pihak mencoba mengendalikan banyak node validator menggunakan satu kunci publik BLS yang sama untuk mendominasi kekuatan quorum secara tidak sah.

Di dalam transaksi STAKE Lumina L1, Execution Engine akan secara aktif memeriksa duplikasi registrasi kunci BLS:

// Pengecekan Sybil Key di crates/state/src/lib.rs if let Some(existing_owner) = self.bls_to_wallet.get(&bls_key) { if existing_owner != sender_wallet { // Deteksi Duplikat! Jail keduanya immediately self.set_validator_status(existing_owner, ValidatorStatus::Jailed); self.set_validator_status(sender_wallet, ValidatorStatus::Jailed); self.set_unstake_allowed(existing_owner, false); self.set_unstake_allowed(sender_wallet, false); ... } }

3. Tata Kelola Banding Desentralisasi (Governance Appeal)

Untuk menghindari kesalahan hukuman akibat bug teknis atau desinkronisasi node pada pelanggaran tingkat menengah (seperti duplikasi BLS), Lumina menyediakan alur banding demokratis terdesentralisasi:

1. Registrasi APPEAL

Validator yang terkena jailing tingkat medium dapat mengirimkan transaksi APPEAL. Status validator berubah menjadi PendingAppeal.

2. Dynamic Voting 75%

Validator aktif lainnya mengirimkan suara persetujuan VOTE_APPEAL:APPROVE. Banding disetujui jika rasio stake penolak/pendukung mencapai minimal 75% dari total kekuatan stake aktif jaringan.

⚖️ Algoritma Persetujuan Deterministik: Perhitungan ambang batas 75% dievaluasi secara dinamis tanpa float division untuk menghindari kerentanan desinkronisasi State Root: total_approve_stake * 4 >= total_active_stake * 3.
