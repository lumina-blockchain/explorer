Securing BFT Quorum: Strict Validator Filtering in P2P Gossip & Consensus

Analisis teknikal bug "Sok-Sokan" Node 4: Mengapa node tanpa stake dilarang keras ikut campur dalam voting konsensus, dan bagaimana perbaikannya menjaga integritas Quorum Certificate (QC) jaringan.

1. Pendahuluan & Latar Belakang Masalah

Pada jaringan blockchain berbasis konsensus BFT (Byzantine Fault Tolerance) seperti Lumina, Quorum Certificate (QC) adalah bukti sah bahwa sebuah blok telah disetujui oleh mayoritas super-mayoritas (> 2/3) validator terdaftar. Integritas dari setiap suara (*vote*) yang membentuk QC bersifat mutlak.

Masalah timbul ketika sebuah simpul non-validator (misalnya, Node 4 yang dijalankan dengan opsi --secret tetapi belum melakukan ikatan dana (*stake*) secara on-chain) secara otomatis ikut berpartisipasi dalam penandatanganan dan penyiaran suara konsensus. Node 4 ini secara tidak sah bertindak seolah-olah ia adalah validator aktif ("sok-sokan" ikut campur BFT) karena berhasil menurunkan kunci privat BLS secara lokal.

⚠️ Gejala Bug di Explorer UI:
Saat Node 4 bergabung tanpa stake, dasbor explorer mendeteksi visualisasi janggal berupa VERIFIED QUORUM: 4/3 VALIDATORS. Hal ini terjadi karena validator aktif keliru mengagregasikan suara Node 4 ke dalam Quorum Certificate, padahal total validator sah di genesis pool hanyalah 3 node.

2. Ancaman Keamanan (Threat Analysis)

Mengapa membiarkan node non-staked memberikan suara konsensus merupakan ancaman fatal?

  • Consensual Gridlock / Network Stall: Fungsi verifikasi QC (verify_quorum_certificate) di Lumina bertindak sangat ketat. Setiap kunci publik penandatangan di dalam QC wajib dicocokkan dengan daftar validator aktif resmi di DB. Jika terdapat satu saja pengirim tanda tangan yang tidak terdaftar/tidak aktif, verifikasi QC akan **gagal total** dan menyebabkan jaringan mogok (stall).
  • Sybil Attack vulnerability: Tanpa filtrasi ketat pada gossip suara, penyerang dapat meluncurkan ribuan node non-staked instan untuk membanjiri P2P network dengan pesan voting palsu (*consensus pollution*), menguras daya CPU validator saat memverifikasi tanda tangan kriptografi BLS yang tidak valid.

3. Desain Solusi & Logika Baru

Untuk menutup celah keamanan ini, kami menerapkan pengamanan ganda di dua gerbang utama P2P Gossip pada berkas node/src/main.rs:

Gerbang 1: Pembatasan Penyiaran Suara Lokal (Auto-Vote Protection)

Sebelum node menandatangani hash blok baru, node wajib memvalidasi identitas dirinya sendiri terhadap daftar validator aktif yang sah:

// 🗳️ Auto-vote untuk block yang diterima if let Some(ref sk) = bls_private_key { let is_active = current_validators.iter().any(|v| v.address.to_string() == local_addr.to_string() && v.status == lumina_staking::ValidatorStatus::Active ); if is_active { // Lakukan penandatanganan BLS dan siarkan ke jaringan! ... } else { // Tetap diam karena kita bukan validator aktif } }

Gerbang 2: Filtrasi Suara Masuk di Sisi Validator (Inbound Vote Filtering)

Saat validator menerima suara konsensus dari jaringan P2P melalui topik VOTES_TOPIC, ia tidak boleh langsung menampungnya di memori kolektor. Validator harus menyaring pengirim secara ketat:

} else if message.topic.as_str() == VOTES_TOPIC { if let Ok((vote, _)) = bincode::decode_from_slice::(&message.data, bincode_config) { let active_validators = consensus.get_active_validators(); let is_active = active_validators.iter().any(|val| val.address.to_string() == vote.validator.to_string() && val.status == lumina_staking::ValidatorStatus::Active ); if is_active { // Proses deteksi double-voting dan kumpulkan ke vote_collector ... } else { tracing::warn!("⚠️ Ignored vote from non-validator or inactive address: {}", vote.validator); } } }

4. Verifikasi Keamanan Jaringan

Setelah perbaikan ini diterapkan dan dikompilasi ulang:

  1. Konsistensi Jumlah Validator: Quorum Certificate kini terbentuk secara presisi dengan rasio 3/3 VALIDATORS (kembali normal). Suara dari Node 4 ditolak mentah-mentah sehingga tidak pernah masuk ke agregasi tanda tangan QC.
  2. Efisiensi Bandwidth & CPU: Validator tidak lagi membuang-buang siklus clock CPU untuk memverifikasi atau menggabungkan tanda tangan dari kunci publik yang tidak terdaftar di database on-chain Lumina.
  3. Stabilitas Tanpa Pengaruh Negatif: Semua integrasi pengujian (jailing, auto-resume, double-voting slashing, dan state transitions) berhasil diselesaikan dengan sukses 100% tanpa regresi logika apa pun.

💡 Kesimpulan:
Dengan arsitektur keamanan baru ini, Lumina Network menjamin batas konsensus (consensus boundary) yang kokoh. Hanya modal komitmen on-chain nyata (Staking) yang berhak memiliki hak suara di jaringan konsensus BFT.
