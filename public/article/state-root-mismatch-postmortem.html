Post-Mortem: Membongkar Bug State Root Mismatch setelah Restart Node

Analisis Kegagalan State Recovery Pasca-Restart Node dan Penyelesaiannya Melalui Selective DB Cleanup di Blockchain Lumina

Dalam sistem blockchain terdistribusi berkecepatan tinggi, kegagalan tak terduga seperti pemadaman listrik, crash proses, atau pematian sengaja dapat menghentikan node validator seketika. Saat node dinyalakan kembali, ia harus memulihkan state internalnya menggunakan mekanisme restorasi state persisten agar dapat segera berpartisipasi kembali dalam jaringan.

Gejala Kritis: Node 1 di-restart pada blok sebelum blok 100 (misalnya blok 70). Pas memutar ulang state dan mencapai Blok #100, transisi epoch pembagian reward berjalan mulus. Namun, begitu masuk ke Blok #101, node mengalami kepanikan konsensus dan crash akibat: State Root Mismatch!

2. Mencari Akar Masalah (The Root Cause Analysis)

Hasil analisis mendalam terhadap modul restore_from_db dan database **Sled** mengungkap dua masalah utama yang memicu cacat konsensus ini:

1. Dynamic Key Double-Accumulation (Akumulasi Ganda DB) 💥

Penyimpanan persisten Sled di tree validator_keys menyimpan status dinamis seperti reward pemimpin epoch (epoch_leader_reward:) dan shared pool (epoch_accumulated_shared_pool). Ketika Node 1 dimatikan di Blok #70 lalu dinyalakan kembali, database persisten tidak dibersihkan. Saat memutar ulang (*delta replay*) dari Blok #1 ke #70, sistem membaca nilai dinamis yang tersisa tersebut dan mengakumulasikannya kembali secara ganda. Hal ini menghasilkan saldo payout yang jauh lebih besar di Blok #100 dibanding node lain, merusak MPT State Root pada Blok #101.

2. Non-Deterministic Validator Sorting (Pengurutan Acak) ⚖️

Ketika mengurutkan validator aktif untuk alokasi reward, sistem melakukan stable sort berdasarkan jumlah stake. Namun, jika ada beberapa validator dengan stake yang sama, urutan relatifnya bersandar pada urutan iterasi DashMap memori yang secara bawaan bersifat acak. Ini menghasilkan pembagian reward ke alamat yang berbeda di antara node-node jaringan.

3. Mismatch Prefiks Pembersihan Dynamic Keys (Appeal & Votes) 📌

Pembersihan selektif pada modul restore_from_db awalnya menggunakan pengecekan prefiks kunci "appeal:" dan "appeal_vote:" untuk menyaring entri dinamis yang perlu dihapus sebelum delta replay dimulai. Namun, pada database riil, data tersebut sebenarnya disimpan dengan prefiks kunci "appeal_status:" dan "appeal_votes:". Karena ketidakcocokan prefiks ini, data status banding (appeal) dan voting banding yang lama tidak terhapus selama delta replay, meninggalkan data kotor di DB yang memicu state mismatch saat memproses blok-blok baru setelah pemulihan.

4. Solusi & Perbaikan Kode (The Technical Cure)

Kami menerapkan dua perbaikan kode di dalam crates/state/src/lib.rs untuk mengatasi kedua kelemahan tersebut:

Perbaikan 1: Dynamic Key Selective Cleanup

Sebelum memutar ulang blok di restore_from_db, kami membersihkan data dinamis yang berkaitan dengan epoch/blok dari database persisten, tetapi tetap mempertahankan kredensial permanen (BLS keys & aliases) agar unit test dan registrasi validator tidak rusak:

self.validator_statuses.clear(); if let Ok(iter) = self.db.iter("validator_keys") { for item in iter { if let Ok((key, _)) = item { let key_str = String::from_utf8_lossy(&key); // 1. Bersihkan parameter dinamis epoch let is_dynamic_epoch = key_str.starts_with("epoch_leader_reward:") || key_str == "epoch_accumulated_shared_pool" || key_str == "epoch_leaders_list" || key_str.starts_with("missed_blocks:"); if is_dynamic_epoch { let _ = self.db.delete("validator_keys", &key); } } } }

Perbaikan 2: Deterministic Stake Tie-Breaker Sorting

Kami menambahkan alamat byte validator (address.0) sebagai *tie-breaker* saat mengurutkan validator dengan stake yang sama, menjamin urutan 100% deterministik:

all_validators.sort_by(|a, b| { b.stake.cmp(&a.stake) .then_with(|| a.address.0.cmp(&b.address.0)) });

Perbaikan 3: Koreksi Prefiks appeal_status dan appeal_votes

Kami menyelaraskan prefiks kunci yang digunakan oleh pembersih database dinamis di crates/state/src/lib.rs agar secara tepat mencocokkan prefiks kunci riil di Sled DB, yaitu "appeal_status:" dan "appeal_votes:" (sebelumnya secara keliru menggunakan "appeal:" dan "appeal_vote:"):

let is_dynamic_status = replay_from <= committed_height && ( key_str.starts_with("validator_status:") || key_str.starts_with("allow_unstake:") || key_str.starts_with("appeal_status:") || key_str.starts_with("appeal_votes:") || key_str.starts_with("stake_height:") );
