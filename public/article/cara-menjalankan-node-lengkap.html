Panduan Menjalankan Node Lumina

Eksplorasi mendalam berbagai arsitektur eksekusi node, skenario pengoperasian jaringan, serta panduan lengkap rujukan parameter CLI otonom.

Node Lumina didesain sebagai sebuah *executable binary* mandiri (berbasis Rust) yang menggabungkan seluruh komponen jaringan *Layer 1*: konsensus BFT HotStuff, VM Smart Contract WASM, database transaksional Sled DB, API Server gRPC/Axum, serta mesin sinkronisasi MPT (*Merkle Patricia Trie*). Fleksibilitas tinggi ini memungkinkan Anda untuk menjalankan node dalam berbagai mode operasional secara dinamis hanya dengan mengubah argumen saat eksekusi.

💡 Catatan Pemulihan Otomatis (Self-Healing MPT): Kode terbaru kami dilengkapi dengan fitur *self-healing* MPT trie. Jika node mendeteksi adanya State Root Mismatch akibat kegagalan database lokal saat runtime, node akan secara otomatis memicu pembangunan ulang state penuh dari genesis menggunakan histori blok DB tanpa memerlukan intervensi manual atau penghapusan data.

1. Berbagai Tipe Node Lumina

Lumina membedakan peran operasional node berdasarkan beban komputasi dan kebutuhan akses data. Terdapat tiga mode operasional utama:

🗳️ Validator Node

Fokus penuh pada validasi transaksi, penciptaan blok baru, serta partisipasi aktif dalam penandatanganan konsensus BFT BLS. Memerlukan kunci rahasia aktif.

🌐 Full Node (Non-Validator)

Bertindak sebagai gerbang API publik. Menyediakan antarmuka RPC Axum, WebSocket PubSub, gRPC Tonic, dan melayani sinkronisasi data explorer tanpa ikut melakukan voting blok.

🔒 Validator-Only Node

Mode yang sangat terisolasi dan aman untuk validator produksi. Menonaktifkan server RPC Axum dan integrasi publik lainnya guna mereduksi celah serangan siber secara maksimal.

2. Berbagai Cara Menjalankan Node Lumina

Cara A: Menggunakan Executable Binary Langsung (Skenario Produksi)

Untuk lingkungan produksi, gunakan binary hasil kompilasi optimal release guna meminimalkan latensi eksekusi transaksi (block-STM) dan memaksimalkan throughput konsensus:

# Kompilasi khusus package lumina-node ke mode release
cargo build --release -p lumina-node

# Eksekusi binary optimal dengan flag spesifik
./target/release/lumina-node \
  --port 61693 \
  --secret 2bb949cc9433ebb2ebe64414de3facbfa825ae98ee95ffd4ae1641abff2e3890 \
  --db-path data/node5 \
  --grpc-port 40063 \
  --telemetry-url http://127.0.0.1:3009/telemetry \
  --telemetry-show-wallet \
  --genesis-path genesis.json \
  --bootnode /ip4/127.0.0.1/tcp/61688/p2p/12D3KooWSC9k5sK1oXzDUjmm4q3rXk4Qok3D9nHsfM3actXRvj3N \
  --fast-sync

Jika tujuan operator adalah menjaga pertumbuhan storage validator tetap terkendali, gunakan mode pruned node. Secara default, tanpa flag pruning, node Lumina tetap berjalan sebagai archive node dan menyimpan seluruh histori block.

# Contoh node pruned yang hanya menyimpan 5 juta block terakhir di disk
cargo run --release -p lumina-node --bin lumina-node -- \
  --port 61696 \
  --db-path data/pruned-node1 \
  --retain-last-blocks 5000000

Cara B: Menggunakan Cargo Run (Skenario Pengembangan)

Sangat ideal untuk proses debugging, penambahan fitur, atau pengujian jangka pendek. Cargo akan menangani kompilasi dan eksekusi secara otomatis:

cargo run --release -p lumina-node --bin lumina-node -- \
  --port 61695 \
  --full-node \
  --db-path data/fullnode1 \
  --grpc-port 40055 \
  --bootnode /ip4/127.0.0.1/tcp/61688/p2p/12D3KooWSC9k5sK1oXzDUjmm4q3rXk4Qok3D9nHsfM3actXRvj3N

Cara C: Menggunakan Python Multi-Node Launcher (Devnet Lokal)

Untuk mensimulasikan cluster jaringan devnet penuh dengan 4 validator independen dan layanan pendukung di komputer lokal Anda:

# Jalankan manajer orchestrator terintegrasi
python .\launcher.py --release --nodes 4

Pilih Menu `[1] 🚀 Jalankan SEMUA Node & Layanan` untuk memulai seluruh cluster secara otomatis, lengkap dengan server telemetri dan bot spammer transaksi.

3. Kamus & Panduan Lengkap Parameter CLI

Berikut adalah rincian lengkap argumen CLI yang didukung oleh kernel utama Lumina Node:

Flag Parameter Tipe Data Mode Default Deskripsi Fungsional & Aturan Operasional
--port / -p u16 61688 Port TCP untuk komunikasi P2P libp2p. Server RPC Axum akan berjalan pada port dinamis: 9090 + (port % 10).
--secret / -s String (Hex) None Seed kunci privat Ed25519 sepanjang 64 karakter hex untuk menurunkan kunci BFT BLS validator.
--bootnode / -b Multiaddr None Multi-address peer pertama yang akan dihubungi untuk terhubung ke mesh network (misal: /ip4/127.0.0.1/tcp/61688/p2p/...).
--db-path String "data/db" Jalur folder penyimpanan persistent database engine Sled DB lokal.
--retain-last-blocks u64 None Mengaktifkan mode pruned node dengan menyimpan hanya N block terakhir di disk. Jika tidak diisi, node tetap menjadi archive node dan menyimpan histori block penuh.
--genesis-path String "genesis.json" Jalur file genesis pemetaan alokasi saldo awal dan validator set. Diperkuat dengan pencarian jalur alternatif.
--fast-sync Flag false Mengaktifkan pemulihan cepat melalui trie snapshot saldo MPT terkini daripada memproses replay transaksi satu per satu.
--full-node Flag false Memaksa node berjalan sebagai node pengamat (observer/gerbang RPC publik) dengan memproses API Axum dan mematikan fungsi voting blok.
--validator-only Flag false Menonaktifkan server API eksternal demi keamanan maksimal, mengisolasi validator hanya pada komunikasi P2P internal konsensus.
--grpc-port u16 50051 Port komunikasi server internal berkinerja tinggi berbasis gRPC Tonic.
--api-key String None API Key khusus untuk mengamankan HTTP REST dan WebSocket JSON-RPC dari akses eksternal tanpa izin.
--rate-limit-max f64 100.0 Kapasitas maksimum ember token (Token Bucket) per alamat IP untuk mencegah serangan spam DoS RPC.
--rate-limit-refill f64 2.0 Laju regenerasi token baru per detik pada sistem rate limiter.
--telemetry-url String "http://..." Target pengiriman data status real-time, statistik TPS, latency, dan histori voting ke server monitoring telemetri.
--telemetry-show-wallet Flag false Menampilkan alamat wallet riil validator di dasbor telemetri publik (secara default disamarkan).
--telegram-token String None Token Bot Telegram untuk integrasi pengiriman log alert kritis langsung ke Telegram pengelola node.
--telegram-chat-id String None Chat ID tujuan pengiriman notifikasi/alert dari Bot Telegram.

🧹 Catatan Pruning Histori Block: Saat --retain-last-blocks aktif, pembersihan block lama tidak dijalankan di jalur panas validasi blok. Sistem akan menunggu snapshot penuh tersedia lebih dulu, lalu melakukan pruning secara bertahap melalui background worker agar beban I/O disk tetap terkendali. Nilai retention yang terlalu kecil juga akan dinaikkan ke batas aman minimum.

4. Alur Otonom Deteksi Identitas & Kunci Rahasia

Lumina memiliki desain zero-configuration untuk kemudahan deployer. Sistem mengelola pemuatan identitas kunci berdasarkan alur prioritas berikut:

  • Pencarian Argumen CLI

    Sistem memprioritaskan pemuatan kunci dari flag --secret. Node akan membaca string hex tersebut sebagai seed Ed25519 aktif.

  • Pencarian Kunci Lokal Disk

    Jika argumen CLI kosong, node memindai file node.key di dalam folder database lokal (sesuai flag --db-path). Jika ditemukan, seed byte dimuat untuk memulihkan identitas lama.

  • Auto-Generation & Persistensi

    Jika kunci tidak ditemukan di manapun, node memicu generator kriptografi otonom untuk membuat pasangan kunci Ed25519 baru, menyimpannya ke disk sebagai node.key, serta mendaftarkan node ke World State.

🛡️ Rekomendasi Pengoperasian Validator Produksi

Dalam lingkungan produksi sesungguhnya, sangat disarankan untuk menjalankan node dengan kombinasi flag --validator-only, menyembunyikan wallet melalui penonaktifan flag --telemetry-show-wallet, serta mengisolasi port gRPC dan RPC di belakang firewall ketat atau VPN korporat guna mengeliminasi vektor serangan DDoS.
