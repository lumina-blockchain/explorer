Mempool Hardening: Proteksi Lumina L1 dari Serangan Nonce Gap & Eksploitasi Sumber Daya

Bedah tuntas implementasi kebijakan Replace-By-Fee (RBF), mitigasi Nonce Gap Bug, dan penambahan kuota transaksi per-akun untuk memastikan sanitasi mempool, keadilan prioritas fee, dan ketahanan terhadap serangan spamming DoS.

Mempool merupakan "ruang tunggu" sebelum transaksi pengguna dijemput oleh validator untuk dieksekusi dan dimasukkan secara permanen ke dalam blok blockchain. Di dalam blockchain Layer-1 berkinerja tinggi seperti **Lumina**, mempool harus dijaga dengan tingkat keamanan ekstra ketat demi mencegah serangan spamming dan kehabisan memori (*out-of-memory crash*).

Hari ini, tim inti Lumina telah merancang dan berhasil merilis paket peningkatan keamanan mempool (Hardening) yang melingkupi tiga fitur mitigasi kritis: **Replace-By-Fee (RBF) Policy**, **Nonce Gap Filter**, dan **Per-Account Pending Transaction Limit (Quota)**. Tiga pilar keamanan ini menjamin pemrosesan transaksi yang adil, efisien, dan kebal dari ancaman spamming.

💡 Catatan Sistem: Seluruh paket mitigasi mempool ini telah ditambal, diuji melalui framework unit-testing secara mandiri, dan berhasil diverifikasi tanpa regresi di seluruh test suite workspace blockchain Lumina.

1. Mengapa Eksploitasi Mempool Harus Dimodifikasi?

Sebelum adanya perbaikan ini, mempool Lumina memiliki celah yang dapat dieksploitasi dengan mudah:

🚨 Kerentanan A: Duplikasi Nonce & Pemborosan RAM
Transaksi diidentifikasi berdasarkan Hash-nya. Jika pengguna mengirim 1.000 transaksi berbeda dengan nonce yang sama tetapi muatan data yang sedikit berbeda, mempool akan menyimpan seluruh 1.000 transaksi tersebut secara paralel karena hash-nya unik. Hal ini dapat membuat RAM validator membengkak pesat.

🚨 Kerentanan B: Nonce Gap & Kemacetan Throughput
Metode pemilihan batch lama mengurutkan transaksi secara global berdasarkan **Fee Tertinggi**. Jika Akun A mengirim transaksi nonce 2 (fee rendah) dan transaksi nonce 3 (fee tinggi), validator akan memprioritaskan nonce 3 karena fee-nya besar. Namun, transaksi nonce 3 tidak akan pernah valid dieksekusi di state karena transaksi nonce 2 belum diproses! Akibatnya, blok dipenuhi transaksi mati yang menyumbat throughput jaringan.

🚨 Kerentanan C: Mempool Starvation & DoS Per-Account
Tidak adanya batasan kuota transaksi per alamat pengirim berarti satu alamat jahat dapat membanjiri mempool dengan mengirimkan ribuan transaksi kecil secara paralel. Tanpa limit, satu akun tunggal bisa memakan habis buffer mempool global (`MAX_MEMPOOL_SIZE`), mencegah pengguna sah lainnya untuk mengirimkan transaksi (*starvation*).

📦 Analogi Dunia Nyata: Sistem Pengiriman Paket Express di Gudang

Bayangkan Anda ingin mengirimkan beberapa buah paket berurutan (Nomor Seri Paket 1, 2, dan 3) menggunakan jasa kurir.

Sebelum Perbaikan (Kemacetan Gudang & Spam) 🤦‍♂️:
1. Anda mengirim Paket 1 dengan tarif normal Rp 10.000, tetapi paket tersebut tertahan lama di gudang karena kurir sedang sibuk. Karena Anda tidak sabar, Anda mengirim Paket 3 (karena Paket 2 hilang/tidak ada) dan membayar tarif express Rp 1.000.000. Gudang kurir memprioritaskan Paket 3 karena bayarannya besar. Namun, konduktor di bandara menolak mengirimkan Paket 3 karena berdasarkan aturan mutlak bea cukai, paket harus dikirim berurutan (Paket 1 dulu, lalu Paket 2, lalu Paket 3). Akibatnya, Paket 3 menggantung sia-sia di bandara, memenuhi ruang kargo pesawat tanpa kegunaan!
2. Seseorang yang jahat memesan 5.000 pengiriman paket kecil sekaligus untuk memonopoli seluruh ruang truk kurir, sehingga pelanggan lain tidak kebagian tempat.

Setelah Perbaikan (Lumina RBF, Nonce Filter, & Limit Per-Account) 🦾:
Sistem gudang Lumina sekarang sangat pintar. 1. Nonce Filter: Kurir akan mengelompokkan paket Anda. Jika dideteksi Anda mengirim Paket 3 tetapi Paket 2 tidak pernah ada di gudang, kurir langsung menyingkirkan Paket 3 dari daftar prioritas pengiriman karena tahu paket tersebut tidak akan lolos bea cukai bandara. 2. Replace-By-Fee (RBF): Jika Anda ingin mempercepat Paket 1 Anda yang tertahan, Anda cukup mengirim paket baru bernomor Seri 1 dengan membayar tarif minimal 10% lebih tinggi (misal Rp 11.000). Kurir akan mencari Paket 1 yang lama, membuangnya, dan menggantinya dengan paket baru yang ber-fee lebih tinggi agar segera dikirim hari itu juga. 3. Limit Per-Account: Setiap pelanggan dibatasi maksimal hanya boleh memiliki 128 paket pending di dalam gudang secara bersamaan. Pengajuan paket ke-129 akan ditolak demi memberikan keadilan bagi pengirim paket lainnya.

2. Implementasi Replace-By-Fee (RBF) & Per-Account Limit

Untuk menertibkan mempool dari duplikasi nonce, memberikan opsi percepatan transaksi, dan mencegah starvation per-akun, kita menyisipkan pengecekan berikut di dalam internal `add_transaction` mempool:

// Cuplikan kode aturan RBF & Quota di crates/mempool/src/lib.rs: let mut existing_hash = None; let mut existing_fee = 0; for entry in self.pending_transactions.iter() { let existing_tx = &entry.value().tx; if existing_tx.transaction.from == tx.transaction.from && existing_tx.transaction.nonce == tx.transaction.nonce { existing_hash = Some(entry.key().clone()); existing_fee = existing_tx.transaction.fee; break; } } if let Some(old_hash) = existing_hash { // Kenaikan fee minimal harus 10% let min_required_fee = existing_fee + (existing_fee / 10).max(1); if tx.transaction.fee >= min_required_fee { // Hapus transaksi lama & izinkan penyisipan transaksi baru self.pending_transactions.remove(&old_hash); tracing::info!("Replace-By-Fee triggered! Replaced transaction..."); } else { return Err("Transaction rejected: New fee is not at least 10% higher than existing fee under RBF policy.".to_string()); } } else { // --- LIMIT TRANSAKSI PER AKUN (BUG 11) --- if self.get_pending_count(&tx.transaction.from) >= MAX_PENDING_PER_ACCOUNT { return Err(format!( "Transaction rejected: Account {:?} has reached the maximum pending transaction limit of {} under Mempool Quota policy.", tx.transaction.from, MAX_PENDING_PER_ACCOUNT )); } }
