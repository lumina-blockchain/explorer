Mempool Optimization: Mengeliminasi Bottleneck O(N log N) dengan BinaryHeap & Pemilihan Berbasis Metadata

Bagaimana Lumina L1 memotong konsumsi CPU dan penggunaan alokasi memori (RAM) pada pemilihan batch transaksi hingga 1000x lipat dengan menghindari kloning global dan menggunakan struktur data prioritas antrean BinaryHeap.

Pada blockchain Layer-1 berkinerja tinggi, **Mempool** (antrean transaksi pending) bertugas menampung puluhan ribu transaksi sebelum dipaketkan ke dalam blok oleh validator. Pemilihan batch transaksi ini (`get_batch`) harus berjalan sangat cepat—dalam hitungan milidetik—agar tidak menghambat siklus proposisi blok hotstuff dan menurunkan performa Transaksi Per Detik (TPS).

Hari ini, tim inti Lumina berhasil mengidentifikasi dan menambal sebuah bottleneck performa kritis (**Bug 13**) pada metode pemilihan batch transaksi mempool dengan mendesain ulang arsitektur pemrosesan data menjadi **Metadata-based Selection** dan memanfaatkan **BinaryHeap** bawaan Rust.

⚡ Hasil Optimasi: Tes alokasi memori membuktikan bahwa dengan mempool berisi 50.000 transaksi, metode baru ini berhasil menghilangkan 49.500+ kloning objek transaksi besar yang tidak perlu, memangkas latensi eksekusi dari detik menjadi milidetik!

1. Masalah Utama: Kloning Global & Pengurutan Berat O(N log N)

Sebelum adanya optimasi ini, metode get_batch di dalam mempool melakukan langkah-langkah berikut di setiap putaran:

🚨 Bottleneck A: Kloning Seluruh Mempool (Global Cloning)
Untuk mengelompokkan transaksi per pengirim (guna menyaring gap nonce), mempool melakukan kloning penuh terhadap seluruh transaksi yang ada. Setiap transaksi membawa tanda tangan kriptografi (Ed25519/BLS), public key, dan payload data (byte smart contract). Kloning 50.000 objek besar ini secara terus-menerus adalah pembunuhan massal bagi performa CPU dan RAM!

🚨 Bottleneck B: Pengurutan Global yang Sia-sia (Global Sort)
Setelah disaring, seluruh transaksi valid diurutkan secara global berdasarkan prioritas fee menggunakan rumus sort_by dengan kompleksitas $O(N \log N)$. Padahal, validator hanya membutuhkan sejumlah kecil transaksi (misalnya limit = 50 atau 500 transaksi) untuk satu blok. Mengurutkan sisa 49.500 transaksi lainnya adalah pemborosan resource komputasi.

📦 Analogi Dunia Nyata: Kantong Belanja Kasir Supermarket

Bayangkan kasir sebuah supermarket raksasa yang super sibuk (validator) ingin memilih 50 barang termahal dari keranjang belanjaan para pelanggan untuk dimasukkan ke dalam kantong belanja premium (blok berikutnya).

Sebelum Perbaikan (Global Cloning & Sorting) 🤦‍♂️:
Kasir meminta pembantunya untuk menyalin secara fisik **setiap barang belanjaan** milik 50.000 pelanggan yang sedang mengantre (membuat tiruan persis sabun, kulkas, beras, TV, dll), lalu menumpuk seluruh barang tiruan tersebut di meja kasir. Kasir kemudian mengurutkan semua barang tiruan itu satu per satu dari yang termahal hingga termurah. Setelah selesai diurutkan, kasir mengambil 50 barang teratas untuk kantong premium, dan **membuang 49.950 barang tiruan lainnya** langsung ke tempat sampah! Proses ini membuat kasir kelelahan, meja kasir penuh sesak (RAM penuh), dan supermarket macet total.

Setelah Perbaikan (Metadata & BinaryHeap) 🦾:
Kasir sekarang bekerja secara cerdas dan modern: 1. Kasir tidak lagi menyalin barang fisik. Kasir hanya meminta **struk kertas kecil (metadata ringan)** yang berisi: Barcode ID, Nomor Antrean (nonce), dan Harga (fee). Struk kertas ini sangat enteng dan murah untuk disalin. 2. Kasir membuang struk pelanggan yang melompati antrean (nonce gap). 3. Kasir menempelkan struk-struk yang valid pada **papan prioritas magnetik (BinaryHeap)**. 4. Kasir tinggal mengambil 50 struk dengan harga tertinggi dari papan prioritas tersebut. 5. Terakhir, kasir mendatangi keranjang belanja asli pelanggan dan **hanya mengambil/menyalin 50 barang fisik asli** yang tertera di struk terpilih tersebut. Sisa 49.950 barang milik pelanggan lain tidak pernah disentuh ataupun diduplikasi!

2. Arsitektur Solusi Baru: Metadata & Priority Queue

Untuk menuntaskan masalah performa ini, kita memecah pemrosesan menjadi dua tahap efisien:

Ekstraksi Metadata Ringan (Hash, Nonce, Fee)
➔
Penyaringan Gap Nonce Lokal per Akun
➔
Heapify BinaryHeap O(N)
➔
Pop Limit Teratas & Kloning Terpilih O(L log N)

Dengan teknik ini, kita memangkas kompleksitas pengerjaan dari $O(N \log N)$ dengan alokasi besar menjadi $O(N)$ untuk heapify metadata ringan ditambah $O(L \log N)$ untuk ekstraksi transaksi terpilih, di mana $L$ (limit) jauh lebih kecil daripada $N$ (mempool size).

3. Implementasi Kode Rust yang Dioptimalkan

Berikut adalah kode performa tinggi yang sekarang berjalan di dalam crates/mempool/src/lib.rs:

pub fn get_batch(&self, limit: usize, state: &Arc<StateManager>) -> Vec<SignedTransaction> { use std::collections::{HashMap, BinaryHeap}; use std::cmp::Ordering; // 1. Definisikan metadata ringan (hanya 48 byte) struct TxMetadataRef { hash: Hash, nonce: u64, fee: u128, } // 2. Definisikan aturan urutan BinaryHeap #[derive(Eq, PartialEq)] struct FeePriorityTx { hash: Hash, nonce: u64, fee: u128, } impl Ord for FeePriorityTx { fn cmp(&self, other: &Self) -> Ordering { // Fee tertinggi diprioritaskan. Jika sama, nonce terendah diprioritaskan. self.fee.cmp(&other.fee) .then_with(|| other.nonce.cmp(&self.nonce)) } } // 3. Kumpulkan metadata ringan pengirim let mut txs_by_sender: HashMap<Address, Vec<TxMetadataRef>> = HashMap::new(); for entry in self.pending_transactions.iter() { let entry_val = entry.value(); txs_by_sender.entry(entry_val.tx.transaction.from.clone()).or_default() .push(TxMetadataRef { hash: entry.key().clone(), nonce: entry_val.tx.transaction.nonce, fee: entry_val.tx.transaction.fee, }); } // [Saring nonce gap per-sender dan kumpulkan di valid_txs...] // 4. Heapify BinaryHeap secara instan O(N) let mut heap = BinaryHeap::with_capacity(valid_txs.len()); for tx in valid_txs { heap.push(FeePriorityTx { hash: tx.hash, nonce: tx.nonce, fee: tx.fee }); } // 5. Pop limit teratas dan lakukan kloning utuh hanya untuk transaksi terpilih let mut result = Vec::with_capacity(limit); while result.len() < limit { if let Some(priority_tx) = heap.pop() { if let Some(entry) = self.pending_transactions.get(&priority_tx.hash) { result.push(entry.value().tx.clone()); // Kloning selektif di sini } } else { break; } } result }

Kesimpulan

Optimasi performa `get_batch` dengan BinaryHeap dan metadata ini adalah langkah krusial untuk memastikan Lumina L1 mampu menampung lonjakan transaksi tinggi tanpa membebani server validator node. Ini memperkuat ketangguhan mempool di bawah beban jaringan tingkat tinggi.
