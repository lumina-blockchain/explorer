Block-STM Speculative Parallel Execution Engine

Bagaimana Lumina L1 melipatgandakan TPS pemrosesan transaksi melalui sandbox multi-versi spekulatif, Rayon thread pooling, dan mitigasi race condition berbasis Thread Pinning.

Dalam sistem blockchain tradisional generasi awal (seperti Bitcoin dan Ethereum Virtual Machine), transaksi dieksekusi secara sekuensial (serial) satu per satu. Meskipun pendekatan ini sangat sederhana dan aman dari race condition, ia membatasi pemanfaatan prosesor modern multi-core. Node validator yang memiliki server mewah dengan puluhan core CPU hanya menggunakan satu core untuk pemrosesan state, menciptakan bottleneck throughput yang sangat parah.

Untuk mengatasi keterbatasan ini, Lumina L1 menghadirkan Block-STM Speculative Parallel Execution Engine. Teknologi ini mengeksekusi banyak transaksi secara bersamaan di thread pool paralel yang aman, lalu mencocokkan hasil bacanya secara deterministik menggunakan pass validasi Optimistic Concurrency Control (OCC) sebelum melakukan batch commit permanen.

💡 Keuntungan Block-STM: Transaksi dari ribuan akun yang berbeda (misalnya A transfer ke B, dan C transfer ke D) berjalan secara 100% paralel murni di core CPU yang berbeda tanpa saling menunggu, menghasilkan skalabilitas level miliaran transaksi per hari.

1. Arsitektur Memori Multi-Versi (MVMemory Isolation)

Agar transaksi yang berjalan paralel tidak merusak state satu sama lain selama eksekusi spekulatif berjalan, Lumina memperkenalkan MVMemory. Struktur ini memegang write-set spekulatif dari setiap transaksi berdasarkan indeksnya dalam blok:

// Struktur transactional memory di crates/state/src/parallel_executor.rs pub struct MVMemory { pub speculative_writes: Vec<RwLock<Option<SpeculativeWriteSet>>>, } impl MVMemory { // Mencari nilai speculative write dari transaksi terdahulu (j < tx_index) pub fn read_account(&self, tx_index: usize, addr: &Address) -> Option<AccountState> { for j in (0..tx_index).rev() { if let Some(ref write_set) = *self.speculative_writes[j].read().unwrap() { if let Some(state) = write_set.accounts.get(addr) { return Some(state.clone()); } } } None } }

2. Pencegahan Konflik Nonce (Account-Based Thread Pinning)

Race condition paling sering terjadi jika akun bot yang sama mengirimkan rentetan transaksi berurutan dalam satu blok. Jika transaksi tersebut dijalankan paralel di thread yang berbeda, pembacaan nonce akan kacau (race condition) dan menyebabkan transaksi batal / dibatalkan secara berulang-ulang.

Lumina memitigasi hal ini secara revolusioner menggunakan Account-Based Thread Pinning. Sebelum grup paralel dimulai, transaksi dikelompokkan berdasarkan alamat pengirimnya. Seluruh transaksi dari pengirim yang sama dipasangkan dan dikunci di thread yang sama untuk memproses nonce secara berurutan, sementara ribuan pengirim lainnya dieksekusi secara konkuren penuh di core CPU yang berbeda.

⚡ Rayon Thread Pool

Membagi beban kerja pemrosesan secara merata ke seluruh core CPU fisik menggunakan library Rayon concurrency.

🛡️ Sandboxing Aman

Database asli (Sled DB) dan state trie diblokir penuh dari operasi tulis spekulatif menggunakan registry callback static thread-local.

4. Kode Pengujian Unit (Unit Test Showcase)

Untuk memastikan performa paralel 100% konsisten secara deterministik dengan model sekuensial, Lumina menyertakan unit test test_block_stm_parallel_execution yang mensimulasikan transfer konkuren antara banyak akun:

#[test] fn test_block_stm_parallel_execution() { let path = get_temp_db_path("parallel_stm"); let db = Arc::new(LuminaDB::open(&path).unwrap()); let state = StateManager::new(db.clone()); // Setup saldo awal akun Alice, Bob, Charlie & David ... // Jalankan parallel_executor spekulatif murni let res = parallel_executor::ParallelExecutor::execute_block_parallel(&state, &txs, &fees); assert!(res.is_ok()); let (statuses, write_sets) = res.unwrap(); assert_eq!(statuses[0], "SUCCESS"); assert_eq!(statuses[1], "SUCCESS"); // Verifikasi bahwa saldo spekulatif diproses terisolasi dengan benar assert_eq!(write_sets[0].accounts.get(&alice).unwrap().balance, 50000 - 1000 - 10); assert_eq!(write_sets[1].accounts.get(&charlie).unwrap().balance, 20000 - 2000 - 15); }
