Decentralized BFT Consensus: Resilient Gossip Vote & Local QC Aggregation

Bedah tuntas arsitektur ketangguhan konsensus HotStuff BFT Lumina L1: mengatasi mati lampu/downtime validator secara otonom, menghilangkan bug kalkulasi quorum, dan menyajikan visualisasi UI yang presisi.

Dalam jaringan blockchain Proof-of-Stake (PoS) berbasis **Byzantine Fault Tolerance (BFT)**, proses pencapaian mufakat di antara puluhan komputer validator online adalah jantung pertahanan sistem. Setiap kali sebuah blok baru diusulkan oleh seorang **Leader**, blok tersebut tidak bisa langsung masuk ke database sebagai kebenaran mutlak. Ia harus dikirimkan ke seluruh validator aktif untuk diperiksa datanya dan ditandatangani suaranya.

Bukti matematis bahwa sebuah proposal blok telah disetujui secara sah oleh lebih dari 2/3 total kekuatan taruhan (*voting power*) validator disebut **Quorum Certificate (QC)**. Namun, metode pengumpulan suara tradisional sering kali memiliki cacat desain bawaan yang rapuh: **ketergantungan absolut pada keaktifan Next Leader**. Jika Next Leader mati lampu atau koneksinya terputus tepat saat validator memberikan suara, sistem akan macet dan liveness jaringan terganggu.

Untuk mengatasi keterbatasan ini secara radikal, Lumina merancang ulang konsensusnya menjadi **Decentralized Local QC Aggregation** di rilis v1.4, didukung oleh tanda tangan kriptografi **BLS12-381 teragregasi** dan transmisi **Gossipsub Mesh Network**.

☕ Analogi Dunia Nyata: Tugas Kelompok di Warkop

Bayangkan kamu sedang mengerjakan tugas kelompok kuliah yang beranggotakan **4 mahasiswa** (Sultan, Founder 2, Founder 3, dan si Staker Baru). Untuk mengesahkan tugas tersebut agar mendapat nilai dari Dosen (masuk ke State Explorer), tugas harus ditandatangani minimal oleh **3 dari 4 orang** kelompok tersebut (Quorum BFT $> 2/3$).

Pola Lama (Leader-Centric) 🤦‍♂️:
Hanya ketua kelompok (Next Leader) yang ditugaskan membawa satu-satunya lembar dokumen tugas asli ke warkop. Anggota lain harus datang bergantian untuk tanda tangan di atas kertas yang sama. Sialnya, malam itu si ketua kelompok mendadak **HP-nya mati dan dia ketiduran di rumah (Offline)**! Meskipun 3 anggota kelompok lainnya sudah siap tanda tangan di warkop, mereka tidak memiliki kertasnya. Tugas tersebut akhirnya **gagal dikumpulkan tepat waktu** (blok menjadi Unverified / parent_qc: null), padahal mayoritas anggota sebenarnya hadir!

Pola Baru Lumina L1 (Decentralized Gossip & Local QC) 🦾:
Sekarena, sistem diubah. Dokumen tugas difotokopi menjadi 4 rangkap, sehingga **masing-masing anggota memegang satu kertas**. Mereka tidak perlu berkumpul fisik di satu meja; mereka cukup saling mengirimkan stiker tanda tangan digital melalui **Grup WhatsApp kelompok (Topik Gossip `lumina-votes`)**.

Setiap kali ada stiker tanda tangan masuk dari anggota lain, masing-masing anggota langsung mencetak dan menempelkannya di lembar fotokopi milik mereka sendiri secara **lokal dan mandiri (Local QC Aggregation)**. Begitu kertas di tangan Sultan sudah berisi 3 tanda tangan sah (dirinya sendiri + Founder 2 + Staker Baru), Sultan **seketika memiliki dokumen tugas yang SAH secara hukum**! Sultan bisa langsung menyebarkannya ke dosen tanpa perlu menunggu si ketua kelompok yang ketiduran bangun. Konsensus berjalan lancar tanpa hambatan!

1. Matematika Byzantine Fault Tolerance: Mengapa Quorum Harus $> 2/3$?

Mengapa dalam rumus BFT, ambang batas persetujuan suara harus lebih besar dari dua pertiga? Hal ini didasarkan pada rumus klasik keamanan Byzantine:

N ≥ 3f + 1

Di mana N adalah total validator aktif, dan f adalah jumlah maksimal validator jahat (*Byzantine*) atau mati (*offline*) yang dapat ditoleransi oleh sistem secara bersamaan:

  • Jika kita memiliki N = 3 validator (Genesis awal), maka kita dapat menoleransi maksimal f = 0 kesalahan. Mengapa? Karena jika ada 1 node mati, sisa 2 node online hanya mewakili $\approx 66.6\%$ stake, yang tidak memenuhi syarat $> 2/3$ ($>66.7\%$). Oleh karena itu, semua node harus hidup 100% untuk memproduksi blok yang verified.
  • Begitu ada **1 staker baru masuk** (seperti yang didelegasikan lewat SDK JavaScript), total validator kita melesat menjadi N = 4. Berdasarkan rumus di atas, dengan $N=4$ kita secara ajaib dapat menoleransi **f = 1 validator mati**!
  • Sebab, jika 1 validator mati, sisa **3 validator yang online** memiliki kekuatan suara sebesar $3/4 \times 100\% = \mathbf{75\%}$. Nilai 75% ini berada di atas syarat quorum $> 66.7\%$, sehingga pembentukan sertifikat (QC) tetap berjalan mulus!

2. Bedah Teknis Bug "133.3%" Quorum

Ketika validator ke-4 (Staker Baru) aktif di jaringan, para developer dikejutkan dengan kemunculan data aneh di halaman detail blok Explorer:

"parent_qc": { "signers_count": 4, "total_validators": 3, "quorum_percentage": "133.3%" }

Kenapa Hal Tersebut Bisa Terjadi?
Akar masalahnya terletak pada **hardcoding** pembagian data di sisi Axum RPC Server. Ketika data dikirimkan secara live melalui WebSocket, data tersebut sudah dihitung dinamis menggunakan panjang array validator sesungguhnya. Namun, pada handler RPC HTTP `/block/:height` dan `/blocks`, kode API internal masih melakukan konversi persentase dengan nilai pembagi statis `3.0` dari era genesis lama:

// ❌ KODE LAMA YANG MENGANDUNG BUG HARDCODED 3 VALIDATOR: "quorum_percentage": format!("{:.1}%", (qc.signers.len() as f64 / 3.0) * 100.0)

Karena total penandatangan (`signers.len()`) bernilai 4, maka pembagiannya menghasilkan $\frac{4}{3} \times 100\% = 133.3\%$. Ini adalah pelanggaran logika matematika blockchain!

Bagaimana Kita Memperbaikinya?
Kita memperbaikinya dengan menghubungkan `StakingState` ke dalam status RPC dan mendefinisikan method penghitung dinamis:

// ✅ KODE BARU YANG DINAMIS DAN VALID: impl RpcState { pub fn get_total_validators(&self) -> usize { let mut total = self.staking.get_validators().len(); for entry in self.state.active_validators.iter() { let addr = entry.value(); if !self.staking.get_validators().iter().any(|v| v.address.to_string() == addr.to_string()) { total += 1; } } total.max(3) // Batas bawah minimal 3 validator genesis } }

Dengan kode di atas, pembagi persentase kini selalu sejalan dengan total validator aktif riil, menjaga kredibilitas kalkulasi konsensus di seluruh endpoint publik!

3. Alur Kerja Komunikasi P2P Gossipsub `lumina-votes`

Setiap kali validator online menerima dan memverifikasi sebuah proposal blok baru, validator tersebut akan menandatangani hash dari proposal tersebut menggunakan BLS Private Key miliknya. Suara yang dihasilkan kemudian dikemas ke dalam sebuah struct `Vote` dan disebarkan ke jaringan mesh network P2P:

Vote Terbentuk di Validator
➔
Siaran Gossipsub (lumina-votes)
➔
Gossip Mesh Delivery ke Semua Peer
➔
Tiap Node Kumpul & Cetak QC Sendiri

Proses transmisi ini menjamin desentralisasi mutlak: **tidak ada satu titik kegagalan (Single Point of Failure)**. Data vote menyebar secara eksponensial dalam hitungan milidetik ke seluruh belahan dunia!
