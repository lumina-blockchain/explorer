State Security: Merkle Patricia Trie & State Root

Bagaimana Lumina mengamankan status kepemilikan aset seluruh jaringan menggunakan pohon kriptografi persisten berkinerja tinggi.

Dalam sistem blockchain Layer 1 modern, salah satu aspek paling krusial yang menentukan keamanan dan skalabilitas adalah bagaimana State (seluruh saldo akun, data kontrak, dan nonce) disimpan, diperbarui, dan diverifikasi secara kriptografis. Tanpa mekanisme yang memadai, jaringan rentan terhadap serangan manipulasi data lokal (double-spending, pemalsuan saldo) dan sinkronisasi lambat.

Lumina mengadopsi Merkle Patricia Trie (MPT) berbasis database persisten Sled, dipadukan dengan penghitungan State Root dinamis pada level konsensus. Dokumen teknis ini membedah arsitektur, implementasi Rust, serta manfaat nyata di balik keputusan desain ini.

💡 Pengumuman Sukses: Fitur Merkle Patricia Trie dan State Root secara resmi telah diimplementasikan 100% pada rilis v1.2, lulus uji coba 13/13 unit test, serta diintegrasikan penuh ke dalam node devnet multi-node!

1. Tantangan Verifikasi State Blockchain

Sebuah node blockchain biasa menyimpan data saldo dalam database pasangan kunci-nilai (key-value store). Ketika node lain menerima blok baru berisi ratusan transaksi, bagaimana ia bisa memverifikasi bahwa pengirim blok tidak merekayasa saldo lokal mereka tanpa mendownload seluruh sejarah database dari hari pertama?

Jawabannya terletak pada **Pohon Kriptografi (Merkle Tree)**. Namun, Merkle Tree biasa memiliki kelemahan: tidak efisien untuk pencarian cepat, penyisipan acak, atau penghapusan kunci. Oleh karena itu, Lumina menggunakan **Merkle Patricia Trie (MPT)**—gabungan harmonis antara Radix Trie (untuk efisiensi navigasi kunci) dan Merkle Tree (untuk integritas kriptografis).

2. Arsitektur Merkle Patricia Trie (MPT) Lumina

Dalam trie kita, setiap alamat dompet 20-byte (160-bit) dipecah menjadi **40 Nibble** (setengah byte / 4-bit) untuk navigasi prefix yang presisi. Sebagai contoh, alamat 0x1a2b... dipecah menjadi:

1 (0001)
→
a (1010)
→
2 (0010)
→
b (1011)
→
...

Trie diorganisasikan ke dalam tiga varian node kriptografis (`TrieNode`) yang diserialisasikan secara efisien ke piringan (database):

Branch Node Memiliki array berisi 16 anak (satu untuk setiap nibble hex 0-f) dan satu nilai opsional.
Extension Node Menyimpan jalur prefix bersama (shared path) untuk menghindari kedalaman pohon yang berlebihan (hemat memori!).
Leaf Node Menandakan ujung akhir dari sebuah kunci, menyimpan sisa nibble kunci dan data aslinya (AccountState).

3. Implementasi Rust: Trie & State Manager

Di bawah ini adalah rancangan representasi data `TrieNode` yang didefinisikan dalam crate lumina-storage dan diintegrasikan ke lumina-state:

#[derive(Clone, Debug, bincode::Encode, bincode::Decode)] pub enum TrieNode { // Branch node dengan 16 child pointer (berisi hash dari node anak) Branch { children: [Option<[u8; 32]>; 16], value: Option<Vec<u8>>, }, // Extension node untuk melompati rute nibbles yang sama Extension { prefix: Vec<u8>, child: [u8; 32], }, // Leaf node menyimpan sisa kunci dan data serialisasi AccountState Leaf { partial: Vec<u8>, value: Vec<u8>, }, }

Di dalam StateManager, setiap kali method update_account(address, account_state) dipanggil pasca eksekusi transaksi, sistem melakukan dua hal secara paralel:

  1. Menyimpan status ter-update ke cache memori berkecepatan tinggi (DashMap) untuk pemrosesan transaksi secepat kilat.
  2. Memperbarui node bersangkutan di dalam Merkle Patricia Trie secara rekursif, yang kemudian menulis data ke database persisten Sled DB.

4. State Root & Alur Konsensus BFT

Desain penempatan State Root Lumina menerapkan pendekatan **Pre-State Root** yang sangat elegan untuk menghindari overhead komputasi ganda (double speculative execution):

1. Block Proposing (Leader)

Leader yang bertugas menyusun blok N mengambil root hash terhitung dari State Trie saat itu: state_root = state_trie.root(). Root ini mencerminkan keadaan dunia persis setelah blok N-1 diterapkan.

2. Block Validation (Validator)

Node validator yang menerima blok N akan membandingkan header.state_root dari blok dengan root trie lokal mereka. Jika berbeda, blok ditolak seketika (mencegah desinkronisasi!).

5. Manfaat Nyata bagi Ekosistem Lumina L1

Implementasi MPT dan State Root dinamis ini menghadirkan lompatan teknologi bagi ekosistem kita:

  • Keamanan BFT Tingkat Tinggi: Mencegah validator jahat (Byzantine) merekayasa saldo lokal mereka karena State Root yang dihasilkan blok mereka pasti ditolak oleh 2/3+ validator jujur lainnya.
  • Dukungan Light Client (HP & Web Browser): Memungkinkan aplikasi dompet mobile melakukan verifikasi saldo secara instan hanya dengan meminta *Merkle Proof* 32-byte tanpa perlu mengunduh database blockchain yang sangat besar.
  • Deteksi Desinkronisasi Instan: Jika terjadi kesalahan eksekusi WASM Smart Contract di salah satu node staker premium, sistem langsung mendeteksi perbedaan State Root seketika pada tinggi blok tersebut dan menghentikan kerusakan lebih lanjut.

Pertanyaan Umum (FAQ)

Apakah MPT memperlambat TPS Lumina?

Tidak signifikan. Berkat caching state di memori (menggunakan DashMap) dan optimalisasi penulisan database asinkron, overhead MPT dapat ditekan seminimal mungkin sehingga performa L1 Lumina tetap mampu melibas ribuan transaksi per detik secara paralel!

Di mana State Root disimpan secara permanen?

State Root disimpan sebagai bagian tak terpisahkan dari `BlockHeader` pada setiap blok yang disimpan di Sled database. Dengan melacak riwayat blok, kita dapat melakukan audit sejarah state pada titik tinggi blok mana pun di masa lalu.
