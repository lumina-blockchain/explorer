High-Throughput Performance Tuning & Latency Optimizations

Bagaimana Lumina L1 memotong latensi hingga 3200% dan menghilangkan bentrokan Optimistic Concurrency Control (OCC) untuk menembus target 20,000+ Transactions Per Second (TPS).

Untuk menembus batas throughput transaksi tingkat elit (20,000+ TPS), sebuah blockchain tidak hanya membutuhkan VM yang cepat, tetapi juga arsitektur konsensus dan pemrosesan state yang bebas hambatan (zero-bottleneck). Dalam pengujian stress test berskala besar menggunakan multi-account spammers, Lumina menghadapi serangkaian batasan performa dunia nyata yang disebabkan oleh bottleneck kriptografi, ketergantungan data terpusat, dan beban I/O terminal.

Dokumen arsitektural ini merangkum serangkaian optimasi performa tingkat lanjut yang berhasil diimplementasikan untuk membuka jalan bagi eksekusi konkuren paralel murni dengan tingkat latensi ultra rendah.

⚡ Rekor Latensi Terpecahkan: Latensi penyusunan blok berhasil dipangkas dari 3.28 detik (3280ms) menjadi hanya 0.1 detik (100ms)—sebuah peningkatan kecepatan luar biasa sebesar 32x lipat (3200% Speedup) pada CPU AMD Ryzen 7 5800H!

1. Hambatan Utama Menuju 20K TPS

Sebelum pembaruan performa ini diterapkan, mesin eksekusi menghadapi tiga bottleneck kritis di bawah beban stress test tinggi:

  • Sponsor Account Hotspot (OCC RAW Conflicts): Fitur Gas Sponsor (Sultan Account) yang membiayai gas fee seluruh transaksi memicu ketergantungan baca-tulis (Read-After-Write) yang parah. Karena setiap transaksi membaca dan menulis saldo sponsor yang sama, Optimistic Concurrency Control (OCC) mendeteksi bentrokan memori spekulatif 100% dari waktu, memaksa seluruh blok dieksekusi secara serial.
  • Serial Cryptographic Signature Verification: Leader konsensus memverifikasi tanda tangan ECDSA secp256k1 secara berurutan satu per satu dalam loop tunggal sebelum memproposalkan blok. Memproses 500+ transaksi memakan waktu 3.2+ detik, membekukan thread utama node untuk sementara waktu.
  • Synchronous Terminal I/O: Konsol Windows PowerShell / CMD terbebani oleh rendering teks ANSI berwarna warni dalam level log INFO yang sangat padat, memakan hingga 50% utilitas thread CPU utama hanya untuk urusan cetak teks di layar.

2. Arsitektur Solusi & Optimasi

A. Deferred Sponsor Settlement (Penyelesaian Sponsor Ditunda)

Untuk meloloskan Block-STM murni tanpa bentrokan memori pada pembayar fee bersama (Sultan Account), Lumina memisahkan pemotongan saldo sponsor dari eksekusi sandboxed paralel:

  1. Selama eksekusi spekulatif paralel, jika fee_payer berbeda dari pengirim transaksi, sistem sengaja melewatkan penulisan saldo sponsor ke memori spekulatif. Ini memastikan tidak ada bentrokan read-write antar transaksi.
  2. Di akhir pemrosesan blok, seluruh gas fee yang dihabiskan oleh transaksi bersponsor dikumpulkan, diakumulasikan, dan dipotong dari saldo sponsor **sekaligus dalam satu kali penulisan database (Batch Commit)**.
// Penundaan pembaruan saldo sponsor di crates/state/src/lib.rs if fee_payer_addr != tx.transaction.from { // Hindari konflik read-write pada akun sponsor yang sama selama eksekusi paralel. // Kita akan kurangi saldo sponsor secara total di akhir blok. if !parallel_executor::ACTIVE_SPECULATIVE_STORE.with(|cell| cell.borrow().is_some()) { self.update_account(fee_payer_addr, payer_state); } }

B. Parallel Signature Pre-Verification via Rayon

Melalui integrasi library konkurensi Rayon, leader memecah tugas verifikasi kriptografi secp256k1 yang sangat berat ke seluruh core logis CPU secara paralel murni:

// Verifikasi paralel murni di crates/consensus/src/lib.rs use rayon::prelude::*; let signature_validities: Vec<bool> = txs.par_iter() .map(|tx| tx.verify()) .collect();

Dengan teknik ini, CPU berspesifikasi tinggi (seperti AMD Ryzen 7 5800H dengan 8 Core / 16 Thread) dapat mendistribusikan 500+ hingga 3000 transaksi ke 16 thread logis secara konkuren penuh, memotong waktu penyusunan proposal secara dramatis.

C. EnvFilter Log Control via Command Line (--quiet / -q)

Modul logging tracing-subscriber dirombak untuk memberikan prioritas penuh kepada variabel lingkungan RUST_LOG:

// Pengaktifan kustomisasi logs dinamis di node/src/main.rs let log_filter = EnvFilter::try_from_default_env() .unwrap_or_else(|_| EnvFilter::new("info")); tracing_subscriber::fmt() .with_env_filter(log_filter) .init();

Dengan ini, launcher dapat menerbangkan node dengan opsi -q atau --quiet yang langsung membungkam logs INFO, melenyapkan hambatan synchronous terminal rendering secara total.

⚡ Zero OCC Conflicts

Transaksi dari pengirim independen berjalan 100% paralel tanpa pernah dibatalkan ulang karena bentrokan saldo sponsor.

🏎️ Lightning Fast Block Propose

Penyusunan proposal blok yang padat transaksi terjadi dalam sekejap mata (< 100ms) berkat verifikasi multi-threading.
