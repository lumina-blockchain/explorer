State Persistence & Self-Healing Recovery

Mekanisme Pemulihan State Otomatis Berbasis Snapshot-First Delta Replay untuk Ketangguhan Node Validator Lumina

Di dalam jaringan blockchain terdistribusi berkecepatan tinggi, kegagalan tak terduga seperti pemadaman listrik, crash proses, atau hilangnya konektivitas dapat menghentikan node validator seketika. Saat node tersebut dinyalakan kembali (restart), status memori internal (seperti saldo akun, state root, data validator aktif) yang hilang harus dibangun kembali dengan cepat dan aman agar node dapat segera berpartisipasi kembali dalam konsensus BFT.

Jika node harus memutar ulang seluruh transaksi sejak blok Genesis #0 (Full Replay), proses tersebut akan memakan waktu berjam-jam bahkan berhari-hari pada jaringan yang padat. Untuk mengatasi masalah efisiensi dan ketangguhan ini, Lumina memperkenalkan sistem **Snapshot-First Delta Replay** dengan fitur **Self-Healing Recovery** otomatis.

Mekanisme Hybrid Startup: Node secara otomatis mendeteksi status database lokal saat booting. Jika data historis terdeteksi, node beralih dari inisialisasi genesis ke restorasi state hibrida, menghemat waktu pemulihan hingga 99.9%!

1. Perbandingan Pemulihan State (Recovery)

Sebelum adanya pemulihan berbasis snapshot, pemulihan data pasca-crash merupakan mimpi buruk bagi validator karena downtime yang lama dapat memicu penalti jailing.

❌ Full Genesis Replay

  • Memutar ulang seluruh transaksi dari blok #0 secara linear.
  • Membutuhkan waktu sangat lama (O(N) terhadap tinggi blok).
  • Menghabiskan daya CPU untuk verifikasi tanda tangan ulang.
  • Validator kehilangan reward blok karena downtime lama.

⚡ Snapshot-First Recovery

  • Memuat potret akun (snapshot) terdekat (kelipatan 100 blok).
  • Melakukan Delta Replay hanya pada blok sisa yang belum masuk snapshot.
  • Memulihkan status validator aktif secara otomatis (Auto-Sync).
  • Kembali aktif dalam milidetik (O(D) di mana D ≤ 100).

2. 3 Komponen Utama Alur Pemulihan Hibrida

1. Atomic Checkpoint & Snapshotting

Pada saat node melakukan commit block (apply_block), node memperbarui checkpoint latest_height secara atomik di database Sled. Setiap 100 blok sekali, snapshot dari World State (Merkle Patricia Trie dan saldo akun) disimpan ke dalam database. Ini membatasi jumlah blok yang perlu diputar ulang setelah crash maksimal hanya 99 blok saja.

2. Delta Replay Engine

Saat restart, engine pemulihan mendeteksi snapshot terakhir yang valid (misalnya pada tinggi #4200) dan memuat state tersebut ke memori. Kemudian, engine memutar ulang sisa blok dari #4201 hingga tinggi checkpoint terakhir yang tercatat di database (misalnya #4287). Proses replay ini berjalan sangat cepat karena database blok sudah ada secara lokal.

3. Automatic Validator Key Synchronizer

Setelah state saldo akun dipulihkan, sistem secara asinkron menyinkronkan kembali set kunci validator aktif (validator_keys) dari state akun ke StakingState engine. Hal ini memastikan node segera mengenali validator mana saja yang berhak melakukan voting tanpa perlu menunggu sinkronisasi P2P luar.

3. Logika Startup Hibrida (Hybrid Bootstrapping)

Kode startup utama pada node/src/main.rs menerapkan percabangan hibrida untuk mendeteksi database yang ada:

// Deteksi DB dan Inisialisasi Hibrida pada node/src/main.rs let db_exists = state.is_db_initialized(); if db_exists { info!("♻️ Database terdeteksi aktif. Memulai restorasi state..."); // Memuat parameter genesis tanpa menimpa DB genesis::load_genesis_parameters(&state, &staking, &genesis_path)?; // Melakukan restorasi snapshot & delta replay state.restore_from_db(&staking)?; } else { info!("🆕 Database kosong. Menginisialisasi Genesis..."); genesis::initialize_genesis(&state, &staking, &genesis_path)?; }

5. Optimasi Deteksi Failover Konsensus (45s → 15s)

Kecepatan pemulihan node hibrida ini juga dipadukan dengan optimasi timeout deteksi failover konsensus. Waktu tunggu keaktifan pemimpin konsensus (consensus leader timeout) diturunkan secara drastis dari **45 detik menjadi 15 detik**.

Alasan Optimasi Timeout: Dalam jaringan berkecepatan tinggi, penundaan selama 45 detik membuat antrean transaksi (mempool) meluap jika leader mati secara tiba-tiba. Dengan timeout 15 detik, node backup mengambil alih kepemimpinan 3x lebih cepat, meminimalkan latensi dan menjaga throughput transaksi tetap stabil.
