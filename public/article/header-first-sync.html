Header-First Sync & Parallel Sync

Mekanisme Sinkronisasi Paralel Terfragmentasi dan Antrean Rak Transit (Out-of-Order Execution Queue) di Blockchain Lumina

Dalam sistem blockchain terdistribusi yang padat aktivitas transaksinya, mengunduh data secara serial sangat lambat dan rawan tersumbat. Apabila satu node saja yang mengirimkan data blok penuh (beserta isinya) lambat, maka sinkronisasi node staker kita akan terganggu.

Lumina memecahkan masalah ini dengan merancang protokol **Header-First & Parallel Sync**. Protokol ini mengamankan verifikasi rantai blok dengan mendownload metadata kepala (*Header*) terlebih dahulu secara sekuensial. Begitu rantai header valid, node staker akan membagi rata unduhan isi transaksi (*Body*) ke seluruh peer yang terhubung secara paralel, menyimpannya di antrean transit, dan mengeksekusinya secara berurutan.

📖 Analogi Dunia Nyata: "Metode Pemesanan Buku Lembaran"

Bayangkan kamu ingin memiliki ensiklopedia 5 volume (Blok #1 sampai #5).

Pendekatan Lama (Full Block Sync): Kamu memanggil satu kurir dan menyuruhnya mengirimkan seluruh buku tebal 5 volume sekaligus. Jika kurir terjebak macet, kamu harus menunggu berjam-jam tanpa memegang apa pun di tanganmu.

Pendekatan Header-First & Parallel (Lumina): Kamu menyuruh kurir kilat membawakan **Daftar Isi & Lembar Halaman Depan** (Header) dari kelima volume buku tersebut terlebih dahulu. Karena sangat ringan, lembaran daftar isi tiba dalam hitungan detik. Kamu memverifikasi urutannya (Daftar isi Vol 1 -> Vol 2 -> dst.).

Setelah daftar isi sah, kamu memanggil **3 Kurir Berbeda sekaligus** (Multi-Peer Parallel) secara bersamaan! Kurir A mengambil isi lembaran Vol 1, Kurir B mengambil Vol 2, dan Kurir C mengambil Vol 3.

Karena jarak toko berbeda, Kurir B (Vol 2) dan Kurir C (Vol 3) tiba lebih cepat daripada Kurir A (Vol 1). Kamu tidak membuang buku tersebut, melainkan menaruhnya di **Rak Buku Transit** (Out-of-Order Cache Queue). Begitu Kurir A (Vol 1) tiba, kamu menyusunnya dan membacanya secara runtut!

1. Perbandingan Arsitektur Sinkronisasi

Bagaimana performa sinkronisasi Header-First Lumina dibandingkan dengan sistem sinkronisasi serial model lama?

Parameter Fitur Model Lama (Serial Full Sync) Lumina (Parallel Header-First Sync)
Kecepatan Unduh Lambat (Tergantung pada 1 single peer) Sangat Cepat (Agregasi paralel dari multi-peer)
Konsumsi Kuota Server Boros (Download full block sampah sebelum diverifikasi) Sangat Kering (Hanya download header sekuensial ringan)
Pertahanan Spam & DoS Lemah (Mudah diserang spam block kosong) Maksimal (Penyaringan header langsung membungkam spam)
Alur Eksekusi Kaku (Harus tiba secara urut sekuensial) Lentur (Antrean transit out-of-order)

2. 3 Pilar Desain Header-First Lumina

1. Sequential Header Verification (Anti DoS)

Node mengunduh serangkaian BlockHeader sekuensial yang sangat ringan. Di balik layar, node memvalidasi bahwa setiap header.number == expected_num dan header.parent_hash == prev_header_hash. Karena header tidak memiliki isi transaksi berat, bandwidth yang digunakan sangat kecil. Hal ini menutup celah serangan spam data transaksi sampah.

2. Dynamic Parallel Partitioning (BitTorrent-like)

Setelah daftar kepala blok divalidasi, node menghitung jumlah peer aktif terhubung. Rentang blok dibagi secara adil dan dikirimkan sebagai permintaan paralel SyncRequest::Bodies. Pendekatan multi-peer ini meningkatkan utilitas bandwidth internet server staker hingga titik maksimal.

3. Merkle Root Match & Out-of-Order Assembly (Rak Transit)

Ketika potongan body transaksi dari berbagai peer tiba tidak berurutan, node menghitung Merkle Transactions Root dari body tersebut secara deterministik (Block::calculate_transactions_root(&body)). Root yang dihitung dicocokkan dengan transactions_root milik header valid. Jika ada peer curang yang memodifikasi isi transaksi, kecurangan terdeteksi seketika! Peer langsung di-disconnect dan dimasukkan ke daftar blokir 24 jam (Score -100 Slashing).

4. Struktur Kode Rust: Engine Sinkronisasi Paralel

Berikut adalah cuplikan teknis bagaimana Lumina mengoordinasikan pembagian dynamic chunking paralel ke banyak peer di dalam loop event libp2p:

// Pembagian chunking dinamis di main.rs let connected_peers: Vec<_> = network.swarm.connected_peers().cloned().collect(); let total_count = valid_headers.len() as u64; let start_h = current_height + 1; if connected_peers.is_empty() { // Fallback ke single peer jika staker stiker tidak ada network.swarm.behaviour_mut().sync.send_request(&peer, SyncRequest::Bodies { start_height: start_h, count: total_count, }); } else { let peer_count = connected_peers.len() as u64; let chunk_size = (total_count + peer_count - 1) / peer_count; let mut distributed_count = 0; for p_id in &connected_peers { if distributed_count >= total_count { break; } let remaining = total_count - distributed_count; let count_for_peer = std::cmp::min(chunk_size, remaining); let start_for_peer = start_h + distributed_count; // Pemicu unduhan paralel dari multi-peer network.swarm.behaviour_mut().sync.send_request(p_id, SyncRequest::Bodies { start_height: start_for_peer, count: count_for_peer, }); distributed_count += count_for_peer; } }

Arsitektur sinkronisasi multi-peer paralel ini menjamin node staker kamu memiliki keandalan tinggi, ketahanan terhadap manipulasi transaksi, dan optimalisasi bandwidth P2P yang maksimal!

B. Penanganan Warning: `Received block body but no matching pending header found!`

Selama pengoperasian, terkadang muncul log peringatan berwarna kuning (warn) seperti di bawah ini:

2026-05-18T06:55:59.606Z WARN lumina_node: ⚠️ [Header-First] Received block body for #305 but no matching pending header found! 2026-05-18T06:55:59.606Z WARN lumina_node: ⚠️ [Header-First] Received block body for #303 but no matching pending header found!

🛡️ Mengapa Peringatan Ini Muncul dan Mengapa Ini Sangat Aman?

1. Penyebab Teknis (Jaringan Asinkron): Ketika node staker kamu dimatikan sementara dan dinyalakan kembali, node membaca state database lokal dari disk dan posisinya sudah berada di blok tinggi (misalnya tinggi #305). Namun, karena latensi internet, peer lain di jaringan baru saja mengirimkan paket transaksi (*bodies*) untuk blok lama (#303 atau #305) hasil dari request antrean bootstrap sebelumnya.

2. Sistem Pengaman Bekerja: Karena blok-blok tersebut sudah sukses disimpan permanen di database lokal, node kamu sudah **membersihkan nomor blok tersebut dari antrean pending** (pending_headers.clear()).

3. Tindakan Node: Ketika respon body lama tiba, engine pendeteksi melihat bahwa nomor blok tidak terdaftar di daftar pending. Node **dengan aman membuang paket usang tersebut**, memberikan peringatan di log, dan terus memproses blok live. Hal ini mencegah terjadinya pemborosan memori cache, duplikasi penyimpanan, dan menjaga integritas state blockchain staker dari serangan replay packet!
